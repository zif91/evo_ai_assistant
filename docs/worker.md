# Cron-воркер на shared-хостинге

Воркер выполняет AI-задания через PHP CLI. Браузер отправляет задание и короткими
запросами получает прогресс. Лимит HTTP-запроса сайта больше не ограничивает всю
генерацию. Панель можно закрыть: воркер продолжит работу.

## Настройка

1. Обновите пакет и повторите установку из README: установщик создаст таблицу заданий
   и обновит JS. Сохранённые настройки и ключ остаются на месте.
2. Уточните в панели хостинга путь к **PHP CLI 8.1–8.4**, путь к сайту и ограничения
   cron-процессов. CLI должен видеть ту же БД и иметь права на `core/storage/`
   (либо фактический `storage_path()` вашей CMS), как PHP сайта.
3. Добавьте задание cron **каждую минуту**. Пример — пути замените своими:

   ```cron
   * * * * * /usr/bin/php /home/USER/site/core/custom/packages/ai-assistant/worker.php --user=1 --max-seconds=50 --prune >> /home/USER/ai-assistant-worker.log 2>&1
   ```

   Если панель отдельно задаёт расписание, вставьте в поле команды только часть
   начиная с `/usr/bin/php`. Лог размещайте вне публичного каталога сайта.
   `--user=1` — ID администратора, который будет отправлять задания. Укажите ID
   своей учётной записи из менеджера. Для другого администратора добавьте отдельное
   cron-задание с его ID. Статус воркера и очередь привязаны к этому пользователю.
4. Для первого запуска выполните ту же команду вручную через терминал или кнопку
   запуска cron в панели. Даже без заданий появится `Worker OK: 0 step(s), 0 failed job(s)`.
5. Обновите **Модули → AI Assistant Settings**. Должны появиться «Cron-воркер доступен»
   и время последнего сигнала. Отправьте новое сообщение: в чате будет
   «Выполняется cron-воркером».

Статус считается актуальным 7 минут: один ответ модели может занимать до 300 секунд.
Первый запуск задания может ждать ближайшего cron до минуты. Обновите страницу
настроек, чтобы увидеть свежий статус.

## Как исполняются задания

- Сохраняются полный контекст модели, полученные вызовы инструментов и результаты.
  API-ключи не копируются в задания; при каждом шаге используются текущие настройки.
- Один шаг — один ответ модели либо одно действие CMS. `--max-seconds=50` ограничивает
  запуск **следующих** шагов, уже начатый ответ модели может занимать до 300 секунд.
  Параметр `provider_timeout` в конфигурации задаёт этот предел (5–900 секунд).
- Параллельные запуски cron не дублируют работу: используется общая файловая блокировка.
  Требуется общий каталог storage для web и CLI; распределённые серверы с разными
  файловыми системами этим воркером не поддерживаются.
- Воркер обрабатывает задания администратора из `--user` (по умолчанию ID 1), чтобы Evolution
  правильно записывала автора изменений. Права администратора проверяются перед каждым
  шагом; удалённый или заблокированный пользователь больше не исполняет задания.
- После остановки процесса следующий cron продолжит с сохранённого шага. Если процесс
  погиб во время действия CMS, результат может быть неопределённым: задание перейдёт
  в `needs_review`, действие автоматически не повторяется. Проверьте страницу и
  задайте продолжение с её ID. Это предотвращает слепое повторное создание страниц.
- При обычной ошибке API кнопка «Повторить AI-шаг» продолжит то же задание с сохранённым
  контекстом. Выполненные действия CMS не повторяются. Для `needs_review` повтор запрещён.
- «Остановить задание» работает между шагами. Уже сохранённые изменения остаются;
  кнопка не откатывает сайт. Создание страниц также не откатывается автоматически.
- `--prune` удаляет завершённые задания и их историю старше 30 дней; активные сохраняются.
  Без этой опции историю нужно периодически очищать самостоятельно.
- `--once` выполняет не более одного шага: удобно для диагностики и проверки восстановления.

## Если воркера нет

Новые задания выполняются пошагово AJAX-запросами, пока открыта панель. При её повторном
открытии незавершённое задание подхватывается. В настройках отображается предупреждение:
**большие задачи могут прерываться по таймауту хостинга; используйте быстрые модели
и дробите задачу на части**. Один медленный ответ модели всё ещё может превышать
лимит PHP-FPM/прокси — AJAX не отменяет ограничения хостинга.

Режим выбирается при создании задания. Уже поставленное в очередь задание ждёт
свой воркер и не переключается автоматически на AJAX. Если cron отключён надолго,
остановите задание в панели, проверьте сохранённые действия и отправьте продолжение.
После включения cron новые задания пойдут на воркер; ранее созданное AJAX-задание
продолжает выполняться через панель.

## Диагностика

- **Воркер не обнаружен:** проверьте cron-лог, версию PHP CLI, расширения, доступ к БД
  и запись в storage. Запускайте именно `worker.php` локальной командой, не URL через curl.
- **Задание ждёт:** cron запускается раз в минуту; проверьте последний сигнал и лог.
  Воркер обрабатывает очередь последовательно.
- **AI step failed:** проверьте API-ключ, модель, баланс/бесплатные лимиты и доступность
  провайдера. Сохранённые действия видны в чате; сообщение провайдера с потенциально
  чувствительными данными не записывается в cron-лог.
- **Хостинг убивает CLI:** cron снимает ограничения HTTP, но не ограничения хостинга
  на процессы, память и исходящие соединения. Для медленных моделей нужен тариф с
  подходящими CLI-лимитами или отдельный исполнитель на сервере.

Воркер не требует Redis, Supervisor, демона или дополнительного API-ключа.
История и контекст содержимого сайта хранятся в БД: включайте их в резервные копии
и учитывайте при настройке срока хранения.
